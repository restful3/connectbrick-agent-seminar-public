    1. 주간 동향 요약 — 에이전트 생태계 2026년 5월

    한 줄 요약 — 모델 성능 경쟁의 다음 병목은 여러 에이전트를 조정하고 운영하는 능력 이다.

    1.1 왜 지금 "에이전트 회사" 인가 — 큰 그림

    2024년 말부터 2025년까지의 흐름은 "모델 한 개의 능력을 어디까지 끌어올릴 수 있나" 의 경쟁이었다. 2026년 5월 현재는 단일 호출의 추론과 도구 사용 품질이 충분히 올라간 결과, 병목이 단일 모델의 지능이 아니라 "여러 호출·도구·사람 승인을 어떻게 조정하고, 어디까지 자율 실행을 맡길 것인가"의 조정 비용 으로 이동했다.

    LangChain의 State of Agent Engineering 2025/2026 설문(1,340명, 2025-11~12 수집)에서 응답자의 57.3%가 에이전트를 실제 운영 환경에 투입 했다고 답했고, 1만 명 이상 대기업으로 좁히면 67%가 운영 단계 다.[1] 이 숫자는 "에이전트가 언젠가 올 것" 이 아니라, 이미 운영 중인 조직이 품질·보안·관찰성 문제를 겪기 시작했다는 신호다.

    이 맥락에서 "한 사람 + N개 에이전트로 운영되는 회사" 라는 아이디어가 실제 도구군으로 굳어졌다. 2026-03 공개된 오픈소스 Paperclip 은 6주 만에 GitHub 53,000+ stars를 모았고, 2026-05-25 GitHub API 기준으로는 67,528 stars 에 도달했다.[2][3] 핵심은 "에이전트를 더 똑똑하게 만든다" 가 아니라 "에이전트들에게 직책·예산·승인 라인을 부여하고 조직도 위에서 운영한다" 는 발상이다. Gartner는 멀티에이전트 시스템 관련 문의가 2024 Q1 → 2025 Q2 +1,445% 증가 했다고 보고했고[4], SK AX도 "2026년부터 10개 이상 에이전트가 협업하는 시스템이 보편화" 라는 국내 전망을 내놓았다.[5]

    처음 읽는 독자는 아래 스택 지도를 먼저 참고하면 된다. 모델은 가장 아래층이다. 그 위에 모델을 장기 실행 작업자로 만드는 에이전트 실행 하네스와 SDK, 도구와 에이전트를 연결하는 프로토콜, 여러 작업자를 배치하는 오케스트레이션, 실제 회사에서 멈춤·승인·추적을 강제하는 운영 규칙이 올라간다.

    1.2 핵심 흐름 5가지

    본 절은 2026년 5월 현재 에이전트 생태계에서 중요한 5가지 흐름을 리포트 본문 안에서 독립적으로 읽히도록 정리한다. 별도 사전 자료를 읽지 않아도 이어지는 2장과 3장의 판단 근거가 되도록, 각 트렌드의 의미와 운영 자동화 관점의 함의를 함께 적는다.

    1.2.1 에이전트 실행 하네스 경쟁 — 코딩 도구에서 업무 실행 환경으로

    2025년의 코딩 에이전트는 주로 개발자 도구였다. 2026년에는 OpenAI Agents SDK · Claude Agent SDK · Google ADK 같은 하네스가 파일 시스템, 샌드박스, 메모리, 도구, 스킬, 파일 수정, 장기 실행을 포함하면서 업무 실행 환경 으로 확장되고 있다.[6][7]

    OpenAI는 2026-04-15 Agents SDK 업데이트에서 설정 가능한 메모리, 샌드박스를 고려한 오케스트레이션, Codex식 파일 시스템 도구, MCP, 스킬, AGENTS.md, 셸 실행, 패치 적용을 공통 구성 요소로 묶었다.[7] 핵심은 모델이 답변만 하는 것이 아니라, 통제된 작업공간에서 파일을 읽고 쓰고, 명령을 실행하고, 중간 상태를 복원하며, 여러 단계 작업을 이어 가는 실행 하네스 를 갖는다는 점이다. Anthropic도 Claude Code 기반 하네스를 Claude Agent SDK로 일반화하며 심층 리서치, 영상 제작, 노트 작성 같은 비코딩 작업을 강조한다.[6]

    왜 중요한가 — "코딩 에이전트 = 개발자 전용"의 구도가 깨지고 있다. Excel · PDF · PPT · 운영 문서 · 광고 리포트처럼 파일 기반 작업이 많은 마케팅/기획 업무도 같은 하네스 위에서 처리할 수 있다. 앞으로 프레임워크 선택은 단순히 "어떤 모델을 쓰나"가 아니라 어떤 작업공간, 샌드박스, 권한 경계, 재시도/복원 방식을 제공하나 의 문제가 된다.

    1.2.2 MCP(Model Context Protocol)의 사실상 표준화

    2024년 11월 Anthropic이 발표한 MCP가 18개월 만에 에이전트-도구/데이터 인터페이스의 사실상 표준 이 됐다. 공개 MCP 서버 레지스트리는 2025년 Q1 1,200개 → 2026년 4월 9,400개+ 로 늘었고, Claude / ChatGPT / Gemini / Cursor / Windsurf / Zed / JetBrains AI / Vercel AI SDK / OpenAI Agents SDK가 모두 MCP를 네이티브로 채택했다.[8][9]

    한 줄 정의 — AI를 위한 USB-C 포트. 어떤 어시스턴트·어떤 모델 패밀리도 어떤 데이터 소스·도구와 호환되도록 공통 어댑터 + 공통 프로토콜 을 마련한 것이 본질이다.[10] 전통 API와의 차이는 실행 중 기능 발견 이다. 에이전트가 실행 중 MCP 서버에 "너는 어떤 일을 할 수 있나?" 를 묻고, 서버가 돌려준 기능 목록에 맞춰 도구 사용법을 조정한다.

    상용 운영에서 남는 위험 4개 — 여러 1차 출처가 공통으로 짚는 운영 위험은 다음이다.[9][10]

    1. 컨텍스트 오염과 폭주 — 범용 MCP 서버를 연결하면 함수 정의와 반환 데이터가 모델 컨텍스트를 빠르게 소모한다.
    2. 인증 / 원격 전송 복잡성 — 원격 MCP 서버는 HTTPS, SSE/Streamable HTTP, 인증 설정이 함께 필요하다.
    3. 품질 편차 — 서버 수가 빠르게 늘면서 권한 범위, 오류 처리, 로그, 데이터 반환 형태 검수가 필수다.
    4. 되돌리기 어려운 행동 — 고객 데이터 삭제, 광고비 집행, 파일 삭제 같은 행동은 MCP 서버 쪽 허용 명령 목록과 승인 게이트가 필요하다.

    MCP 공식 로드맵도 2026년 우선순위로 전송 확장성, 거버넌스 성숙도, 기업 도입 준비도를 잡고, 감사 로그, SSO 통합 인증, 게이트웨이 동작, 설정 이식성을 기업 채택 과제로 명시한다.[9] Docker MCP Gateway 같은 중앙 인증·비밀값 관리 패턴은 이 간극을 메우는 구현안 중 하나다.[27] 쉽게 말해 각 앱이 서버마다 API 키와 실행 설정을 따로 들고 있지 않고, 게이트웨이가 서버 실행·라우팅·인증·자격증명 관리를 대신한다. 그래서 아래 그림은 "호스트가 모든 도구에 직접 붙는다"가 아니라, "호스트는 게이트웨이에 붙고 게이트웨이가 MCP 서버와 데이터 소스를 통제한다"로 읽으면 된다.

    운영 자동화 관점 — Shopify · Meta Ads · Instagram · GA4 · Slack 같은 외부 시스템은 MCP 서버를 한 번 만들어 두면 모든 에이전트가 함께 사용할 수 있다. 단 범용 MCP를 무분별하게 연결하면 컨텍스트 폭주가 곧 비용 폭주로 이어진다. 자체 자산은 목적이 좁은 전용 MCP로 정밀하게 설계하고, 외부 SaaS는 게이트웨이 같은 통합 진입점을 거치는 패턴이 안전하다.

    1.2.3 A2A와 프로토콜 계층화 — 도구 연결 다음은 에이전트 간 연결

    MCP가 에이전트와 도구/데이터를 잇는 표준이라면, Google의 A2A(Agent2Agent) 는 에이전트와 에이전트를 잇는 표준을 겨냥한다. Google은 A2A를 2025-04-09 공개하면서, 서로 다른 벤더·프레임워크의 에이전트가 서로를 발견하고, 소통하고, 조율하도록 하는 공개 프로토콜이라고 설명했고, MCP를 보완한다고 명시했다.[11] 출시 시점에 Atlassian, Box, Cohere, MongoDB, PayPal, Salesforce, SAP, ServiceNow, Workday 등 50개 이상 파트너가 참여했다.[11]

    Google의 2026-03 Developer's Guide to AI Agent Protocols 는 MCP, A2A, UCP, AP2, A2UI, AG-UI를 경쟁 표준이 아니라 계층별 문제 해결 도구 로 정리한다.[12]

    표 31.2.3 A2A와 프로토콜 계층화 — 도구 연결 다음은 에이전트 간 연결
    계층 해결하는 문제 운영 자동화 예시
    MCP 에이전트가 도구·데이터에 접근 CRM, 사내 DB, Drive, Slack
    A2A 에이전트가 다른 전문 에이전트를 발견·호출 리서치 agent, 검수 agent, 데이터 분석 agent
    UCP/AP2 상거래·결제 흐름 표준화 구매 요청, 결제 승인, 예산 한도
    A2UI/AG-UI 결과 UI와 실시간 이벤트 작업 진행 대시보드, 승인 큐, 실시간 상태

    왜 중요한가 — "MCP를 연결하면 멀티에이전트가 된다" 는 말은 절반만 맞다. MCP는 도구 접근을 표준화하지만, 서로 다른 전문 에이전트가 어떤 계약으로 요청을 주고받을지는 별도 문제다. 2026년의 표준화 경쟁은 MCP 단일 표준 이 아니라, 도구 / 에이전트 / 상거래 / 결제 / UI 로 나뉜 프로토콜 스택의 정리로 보는 편이 정확하다.

    1.2.4 Agent Skills — 프롬프트 자산의 코드화

    Anthropic이 2025-10 Agent Skills를 공개했고, 2025-12-18에는 여러 플랫폼에 이식 가능한 공개 표준으로 확장했다.[13][14] 폴더 하나에 SKILL.md(파일 맨 앞의 구조화된 메타데이터 + Markdown 지시문)와 보조 스크립트/리소스를 담는 단순 포맷이다. 핵심은 필요할 때만 단계적으로 불러오는 방식 이다. 시작 시에는 스킬 이름·설명·호출 조건만 읽고, 실제로 필요할 때만 본문과 리소스를 컨텍스트에 올려 토큰 비용을 줄인다.

    왜 중요한가 — 그동안 사내에 흩어져 있던 "ChatGPT 프롬프트 모음.docx" , "노션 프롬프트 라이브러리" 같은 비공식 자산이 버전 관리 가능한 코드 디렉토리 가 된다. 예를 들어 보고서 작성 기준 / 데이터 검수 절차 / 반복 실행 스크립트 를 각각 스킬 폴더로 정리하면, 같은 자산을 Claude Code · Cursor · Paperclip의 모든 에이전트가 동일하게 호출할 수 있다.

    초심자 관점에서 스킬은 "좋은 프롬프트 모음"보다 넓은 개념이다. 한 스킬은 특정 작업을 잘 수행하기 위해 필요한 설명서, 예시, 체크리스트, 템플릿, 보조 스크립트, 금지 규칙 을 한 폴더에 묶은 능력 패키지에 가깝다. 평소에는 이름과 설명만 보이다가, 해당 작업이 필요할 때만 본문과 리소스를 불러온다. 그래서 에이전트는 매번 긴 지침을 전부 읽지 않고도 "보고서 초안 작성", "데이터 품질 점검", "발행 전 검수" 같은 반복 작업의 기준을 일관되게 적용할 수 있다.

    1.2.5 관찰성·평가·비용 — 운영 규칙의 표준화

    에이전트가 실제 운영으로 들어가면서 "잘 돌아가는 것처럼 보이는가"보다 왜 그런 결정을 했는지 추적하고, 실패를 재현하고, 비용을 제어할 수 있는가 가 중요해졌다. LangChain 설문 기준 상용 운영 팀의 89%가 관찰성(observability)을 도입 했고, 62%는 단계별 실행·도구 호출 단위 추적을 본다. 평가 지표도 배포 전 고정 테스트셋으로 검증하는 오프라인 평가와, 운영 중 실제 요청을 샘플링해 품질·비용·실패율을 보는 온라인 평가로 나뉘며, 도입률은 각각 52.4%, 37.3%다.[1]

    왜 중요한가 — 멀티 에이전트가 늘어날수록 "왜 이 결과가 나왔는지" 의 사후 추적성이 상용 운영의 핵심 요건이 된다. LangChain 설문에서 상용 운영 진입을 가로막는 1위 이유가 품질(32%) 이었는데, 관찰성 없는 품질 개선은 불가능하다.[1] 10,000명 이상 대기업에서는 보안이 두 번째 우려로 올라와, 권한·감사·승인 정책이 오케스트레이션 설계의 일부가 된다.[1]

    평가 영역에서는 코딩의 SWE-bench가 가장 흔히 언급되는 척도지만, 코딩 외 영역은 AgentBench / GAIA / TAU-bench / WebArena 같은 벤치마크가 있어도 합의된 표준은 아직 약하다.[15] 그래서 상용 운영의 핵심 질문은 "벤치마크 1등 모델은 무엇인가"가 아니라 우리 도메인의 단계별 실패율과 사람 승인 기준을 측정하고 있는가 다.

    복리 오류는 이 문제를 직관적으로 보여 준다.[16]

    • 단계당 90% × 5단계 = 59%
    • 단계당 95% × 10단계 = 60%

    외부 발행·고객 접점·비용 집행처럼 5~10 단계가 직렬로 진행되는 작업 흐름에서는 단계별 95% 이상이거나 HITL 체크포인트가 반드시 포함되어야 한다.

    비용도 같은 축이다. Claude Agent SDK · claude -p · GitHub Actions의 구독 토큰이 별도 크레딧 버킷으로 분리되는 정책 변화처럼, 사용량이 큰 에이전트 작업 흐름의 가격 모델은 계속 재편되고 있다.[17] 따라서 어댑터 단계에서 60/30/10 모델 라우팅 + Iceberg + 하위 에이전트 격리 같은 비용 인지형 설계를 기본값으로 두는 편이 안전하다.[16]

    1.3 운영 자동화 관점 — 논의거리 3가지

    자세한 적용 논의는 별도 시연과 질의응답에서 이어가고, 여기서는 논의거리만 제시한다.

    1. 조직형 오케스트레이션의 자연스러움 — Paperclip식 조직도 + 예산·승인 라인 모델은 프로젝트 단위 산출물 + 사람 승인 + 비용 한도 가 함께 있는 업무에 특히 적합하다.
    2. MCP + A2A = 통합 효과가 가장 큰 영역 — CRM · 사내 DB · Drive · Slack 같은 시스템은 MCP로 감싸고, 리서치·검수·데이터 분석 같은 전문 에이전트는 A2A식 계약으로 연결하는 구도가 자연스럽다.
    3. 반복 기준 = SKILL.md로 자산화 — 작성 기준 · 검수 규칙 · 템플릿 · 금지 규칙을 에이전트 스킬로 패키징하면 Claude · Cursor · Paperclip 어디서든 동일 기준을 적용할 수 있다. 흩어진 프롬프트 때문에 발생하는 일관성 문제에 대한 구조적 해법이다.

    2. 에이전트 오케스트레이션의 유형

    이 장의 한 줄 — 에이전트 오케스트레이션은 "어느 라이브러리가 좋은가"가 아니라 일을 어떤 단위로 나누고, 누가 다음 행동을 정하며, 어디서 멈출 것인가 를 설계하는 문제다.

    1장에서 본 것처럼 단일 모델 능력만으로 차이를 만들던 시기는 지나가고 있다. 2026년의 선택지는 "어떤 모델의 성능이 더 높은가"보다 여러 호출·도구·사람 승인을 어떤 구조로 엮을 것인가 에 가까워졌다. 본 장은 이 선택지를 그래프형 / 역할·핸드오프형 / 조직형 세 가지 오케스트레이션 유형으로 정리하고, 그 위에 얹히는 감독자·라우터 와 스킬 을 보조 패턴으로 분리한다.

    이 분류는 새로운 학술 분류가 아니라, Anthropic의 작업 흐름/에이전트 구분[18], LangChain/LangGraph의 멀티에이전트 패턴[19], 멀티에이전트 협업 연구[20]를 발표 흐름에 맞게 단순화한 것이다. 판단 기준은 단순하다. 우리 업무는 흐름으로 제어해야 하는가, 역할 인계로 풀어야 하는가, 조직 운영 모델로 관리해야 하는가.

    2.1 그래프형 (LangGraph)

    기존 패턴으로 보면 — 그래프형은 "정해진 절차 안에서 LLM과 도구를 호출하는" 방식에 가깝다. 리서치 → 초안 → 검수 → 발행처럼 단계와 분기, 승인 지점을 코드로 그릴 수 있을 때 잘 맞는다. Anthropic의 작업 흐름 구분과 LangChain의 맞춤형 작업 흐름이 이 관점을 뒷받침한다.[18][19]

    사고 방식

    그래프형(graph-based) 의 사고 방식은 상태 그래프(state graph) + 노드(node) + 엣지(edge) + 체크포인트(checkpoint) 다. 작업 흐름을 노드(에이전트 또는 도구 호출 한 단계)와 엣지(다음 노드로 가는 조건부 전이)로 명시적으로 그리고, 각 노드의 입출력은 공유 상태 객체에 누적된다. LangGraph의 차별점은 노드 사이에 HITL(human-in-the-loop) 체크포인트 를 기본 기능으로 삽입할 수 있다는 점이다. 특정 엣지에서 실행을 멈추고 사람 승인을 기다린 뒤 재개하는 패턴이 SDK 수준에서 지원된다.

    구조 예시 (의사코드)

    코드 1구조 예시 (의사코드)
    from langgraph.graph import StateGraph, END

graph = StateGraph(ProjectState)
graph.add_node("research", research_agent)
graph.add_node("draft", writer_agent)
graph.add_node("review", human_approval)         # HITL 체크포인트
graph.add_node("publish", publisher_agent)

graph.add_edge("research", "draft")
graph.add_edge("draft", "review")
graph.add_conditional_edges(
    "review",
    lambda s: "publish" if s.approved else "draft",  # 반려 시 draft 재실행
)
graph.add_edge("publish", END)

    잘 맞는 작업 흐름

    분기가 결정적(deterministic) 이고 단계 수가 미리 알려진 작업 흐름 — 예: 리서치 → 초안 → 검수 → 발행 처럼 노드 개수와 순서가 거의 고정된 파이프라인. 분기 조건을 코드로 명시할 수 있고, HITL 체크포인트가 자연스러운 자리에 들어가는 작업이라면 그래프형이 가장 추적성이 높다. 반대로, 단계 수 자체가 LLM의 판단에 따라 가변적이거나 발산적 토론이 필요한 작업에는 그래프가 지나치게 복잡해진다.

    의사결정 포인트

    그래프형의 장점은 흐름을 눈에 보이게 고정한다 는 데 있다. 어느 단계에서 멈췄는지, 승인 후 어디로 갔는지, 반려되면 어느 노드로 돌아가는지를 코드와 체크포인트로 남기기 쉽다. 그래서 승인 지점이 정해진 업무에는 강하지만, 승인·예산·담당자 배정이 여러 프로젝트 전체에 걸쳐 움직이는 경우에는 별도 운영 규칙을 덧붙여야 한다. 즉 그래프형은 절차가 또렷한 파이프라인 에 적합하고, 조직 전체의 위임·예산 운영까지 표현하려면 다른 구조와 결합하는 편이 자연스럽다.

    2.2 역할·핸드오프형 (CrewAI, AutoGen)

    기존 패턴으로 보면 — 역할·핸드오프형은 한 에이전트가 끝까지 끌고 가는 구조가 아니라, 상황에 따라 다음 담당자에게 주도권이 넘어가는 방식이다. 리서처가 자료를 찾고, 작성자가 초안을 만들고, 비평가가 반려하거나 통과시키는 식이다. LangChain/OpenAI의 인계 방식, CrewAI의 팀 구성, AutoGen의 GroupChat이 이 흐름과 닿아 있다.[19][21][22][23]

    사고 방식

    역할·핸드오프형(role/handoff-based) 의 사고 방식은 역할(role) + 대화(conversation) + 인계(handoff) 다. 각 에이전트는 직책(researcher / writer / critic 등)과 책임 범위를 받고, 작업은 누가 어떤 관점으로 말하고 다음 담당자에게 넘기는가 에 따라 산출된다. CrewAI는 이를 "절차 기반 팀 구성"으로 정형화하고, AutoGen / AG2는 GroupChat 추상으로 다자 대화를 핵심 기능으로 만든다. OpenAI와 LangChain의 인계 패턴처럼, 특정 시점에 대화의 주도권이 다른 에이전트로 넘어가는 구현도 여기에 속한다.

    구조 예시 (YAML, CrewAI 스타일)

    코드 2구조 예시 (YAML, CrewAI 스타일)
    crew:
  agents:
    - role: trend_researcher
      goal: 관련 자료와 시장 신호 5건 발굴
    - role: writer
      goal: 발굴 자료 기반 초안 3안 작성
    - role: critic
      goal: 논리, 근거, 표현 리스크 지적 + 반려/통과 판정
  process: sequential   # 또는 hierarchical (manager 지정)
  tasks:
    - description: 5개 자료 리서치
      agent: trend_researcher
    - description: 초안 3안 → critic 피드백 → 수정
      agents: [writer, critic]

    잘 맞는 워크플로

    발산적 브레인스토밍, 다관점 검토, 합의 형성 이 본질인 작업 — 예: 문제 정의, 대안 발굴, 초안 후보 생성, 다관점 리뷰. 단계가 미리 정해져 있지 않고 "누가 무엇을 말하는가" 의 관점 차이가 산출물 품질을 좌우하는 영역. 반대로, 산출물의 형태와 승인 라인이 명확히 고정된 운영 워크플로에는 대화형 구조가 과해질 수 있다. 수렴이 느리거나 무한 핑퐁이 발생하기 쉽다.

    의사결정 포인트

    역할·핸드오프형에서 중요한 단위는 노드가 아니라 담당자 전환과 발언 순서 다. 리서처, 작성자, 비평가가 서로 다른 관점으로 말하면서 초안의 폭을 넓히고 허점을 찾는 데 강하다. 다만 승인이나 예산처럼 반드시 지켜야 하는 규칙은 대화 참여자 중 누군가가 계속 기억하고 적용해야 하므로, 시스템이 강제로 멈춰 세우는 구조보다 약하다. 그래서 역할·핸드오프형은 최종 운영 통제 장치라기보다, 아이디어를 만들고 여러 관점으로 검토하는 발산·비평 단계 에 특히 잘 맞는다.

    2.3 조직형 (Paperclip)

    기존 패턴으로 보면 — 조직형은 감독자 구조나 계층형 멀티에이전트 구조처럼 여러 담당자에게 일을 나누는 방식과 닮았다.[19] 차이는 "누구에게 맡길지"에서 끝나지 않는다는 점이다. 조직형은 승인 대기, 예산 한도, 감사 로그처럼 일이 멈춰야 하는 조건까지 시스템의 기본 규칙으로 둔다.

    사고 방식

    조직형(organization-based) 의 사고 방식은 회사 단위(company) — 조직도(org chart) + 목표(goal) + 예산(budget) + 운영 통제(governance) 다. 에이전트는 "역할" 이 아니라 직책 + 보고 라인 + 예산 한도 + 승인 권한 을 가진 직원 으로 모델링되고, 일감은 회의·메시지가 아니라 이슈 / 작업 / 목표 라는 산출물 단위로 흘러간다. 결정적 차별점은 운영 통제를 실행 중 시스템이 강제한다는 점이다. 승인 큐에 걸린 전략은 단순 알림이 아니라, 미승인 시 하위 작업 진행 자체를 시스템이 차단한다. 예산도 80% 사전 경고 / 100% 강제 중단으로 추적되어 자동 일시정지를 수행한다.

    의사결정 포인트

    조직형은 단순히 "여러 에이전트가 있다"는 뜻이 아니다. 누가 맡는지, 어떤 목표의 일부인지, 어디서 사람 승인이 필요한지, 어느 예산 한도 안에서 움직이는지가 같은 시스템 안에 묶여야 조직형에 가깝다. 그래서 핵심 단위도 대화나 노드가 아니라 이슈 / 작업 이다. 승인 큐와 예산 한도는 권고 사항이 아니라 실행을 멈추는 조건이 되며, 이 점이 일반적인 감독자 구조와 가장 크게 다르다. 프로젝트 단위 산출물, 사람 승인, 비용 한도, 병렬 위임이 동시에 있는 업무라면 조직형 사고 방식이 자연스러운 출발점이 된다.

    3장에서 확인할 사례

    본 리포트 3장에서는 Paperclip을 조직형 패러다임의 사례로 본다. 핵심은 내부 구현 전체를 외우는 것이 아니라, 목표가 이슈로 쪼개지고, 조직도 위에서 위임되며, 승인·예산이 실행 중 차단 규칙으로 작동한다 는 점을 확인하는 것이다.

    2.4 보조 패턴 — 감독자·라우터

    위상 정리 — 감독자·라우터는 독립된 오케스트레이션 유형이라기보다, 그래프형·역할형·조직형 안에 들어가는 제어 패턴 이다. 핵심 질문은 "다음 작업자나 경로를 누가 고르는가"다.

    Anthropic의 라우팅 / 조정자-작업자 패턴[18], LangChain의 감독자 / 하위 에이전트 패턴[19], CrewAI의 계층형 절차는 모두 중앙 조정자가 작업을 해석하고, 적절한 작업자나 전문 에이전트에게 일을 넘긴다는 점에서 닮아 있다. 다만 이것을 그래프형·역할형·조직형과 같은 레벨의 "네 번째 유형"으로 두면 레이어가 섞인다. 감독자·라우터는 어느 구조에도 들어갈 수 있는 선택 장치 에 가깝다.

    1. 단계와 승인 지점이 고정되어 있으면 그래프형을 먼저 본다.
    2. 관점 전환과 비평이 품질을 좌우하면 역할·핸드오프형을 먼저 본다.

    2.7 실무 보정 — 실제 운영은 하이브리드다

    마지막으로 한 가지를 분명히 해야 한다. 실제 상용 운영 시스템이 위 세 유형 중 하나에 정확히 들어맞는 경우는 드물다. 이 분류는 처음 설계를 어디서 시작할지 를 정하는 프레임이지, 최종 아키텍처의 이름표가 아니다.

    실무에서는 보통 다음 보정이 들어간다.

    1. 시각 워크플로 도구 — n8n, Make, Zapier 같은 도구는 개발자가 아닌 운영자에게 적합하다. 카피 발행, 이메일 온보딩, 리드 수집처럼 결정적이고 반복적인 파이프라인은 코드형 그래프보다 시각 도구가 더 빨리 정착할 수 있다.
    2. 감독자·라우터 제어 — 요청 종류가 다양하면 중앙 감독자나 라우터가 다음 작업자와 경로를 고르는 패턴이 필요하다. 이것은 별도 유형이라기보다 그래프형의 분기 노드, 역할형의 관리자, 조직형의 상위 직책으로 구현된다.
    3. 개발자용 에이전트 플랫폼 — Google Antigravity, Claude Code Agent Teams/Agent View 같은 도구는 노코드 업무 자동화보다 개발자 워크스페이스에서 여러 에이전트 세션을 실행·검증·관찰·조정하는 쪽에 가깝다.[24] n8n류와 같은 칸에 넣기보다, 에이전트 실행 하네스, 개발 환경, 작업 격리, 권한 제어, 오케스트레이션 UI가 결합된 범주로 보는 편이 정확하다. Claude Code의 subagents는 세션 내부 위임 패턴에 가깝고, Agent Teams나 Agent View는 여러 독립 세션을 관리하는 플랫폼 성격이 더 강하다.
    4. 도메인 맞춤형 구조 — LangChain의 멀티에이전트 가이드가 강조하듯, 실전에서는 하위 에이전트 / 인계 / 스킬 / 라우터 / 맞춤형 작업 흐름을 조합한다.[19] 예를 들어 조직형 뼈대 위에 작업 배분은 감독자·라우터로, 작성 단계는 역할·핸드오프형으로, 반복 검수 기준은 스킬로, 승인 라인은 그래프형 체크포인트로 결합할 수 있다.

    따라서 2회차의 질문은 "세 유형 중 하나를 고르자" 가 아니다. 더 정확한 질문은 다음이다.

    우리의 기본 뼈대는 무엇이고, 어느 단계에 어떤 보조 패턴을 섞어야 하는가?

    본 세미나는 이 질문에 대한 출발점으로 조직형 뼈대 + 스킬 자산 + 명시적 승인 게이트 를 제안한다. 실제 판단은 커넥트브릭의 업무 시나리오, 승인 책임, 채널 운영 방식, 비용 한도를 놓고 2회차에서 함께 조정해야 한다.

    3. 조직형 패러다임 사례 — Paperclip

    이 장의 한 줄 — Paperclip은 "에이전트가 더 똑똑하게 말하게 하는 도구"라기보다, 여러 에이전트가 일할 때 누가 맡고, 어디서 멈추고, 무엇을 승인받는지 를 회사 운영 모델로 표현한 사례다.

    2장에서 본 오케스트레이션 유형 중 조직형은 가장 낯설다. 그래프형은 플로우차트, 역할·핸드오프형은 회의와 인계로 설명할 수 있다. 반면 조직형은 에이전트를 직원처럼 배치하고, 일을 이슈로 나누고, 승인과 예산을 실행 중 규칙으로 강제 한다. 스킬은 이 구조 안에서 각 에이전트가 공유하는 능력 자산으로 붙는다.

    Paperclip을 보는 이유는 Paperclip 자체가 정답이라서가 아니다. 조직형 사고 방식이 실제 시스템에서는 어떤 모양을 갖는지 보여 주는 좋은 사례이기 때문이다.

    3.1 한 줄 정의 — 에이전트 팀을 회사처럼 운영한다

    Paperclip은 오픈소스 에이전트 오케스트레이션 플랫폼 이다. Node.js 서버, React UI, PostgreSQL 위에 하트비트 기반 작업 큐와 조직도, 이슈, 승인, 예산 추적을 얹어 외부 에이전트 실행 환경을 관리한다.[25][26]

    공식 설명에서 가장 중요한 문장은 다음이다.[25]

    "If OpenClaw is an employee, Paperclip is the company."

    즉 Paperclip의 은유는 "좋은 에이전트 한 명"이 아니라 회사 다. 사람은 목표를 주고, CEO 에이전트는 일을 쪼개고, 하위 에이전트는 이슈를 처리하며, 중요한 결정은 승인 큐에서 멈춘다.

    조직도(Org Chart) CEO와 하위 에이전트의 보고 라인 위임과 에스컬레이션의 경로
    이슈(Issue) 더 이상 쪼개지 않는 작업 단위 실행·로그·승인의 단위

    이 구조의 장점은 목표와 작업의 연결이 끊기지 않는다는 점이다. 하나의 이슈는 어떤 회사, 어떤 프로젝트, 어떤 상위 목표, 어떤 담당 에이전트에 속하는지 추적된다. 그래서 실행 결과를 볼 때도 "이 에이전트가 무슨 말을 했나"가 아니라 "이 목표를 위해 어떤 이슈가 어떻게 처리됐나" 로 볼 수 있다.

    3.3 하트비트 — 계속 도는 루프가 아니라 깨워서 일시키는 루프

    Paperclip의 실행 모델은 하트비트 다. 에이전트가 무한히 돌아다니며 일을 찾는 방식이 아니라, 이슈가 큐에 들어오면 에이전트를 깨우고, 작업 컨텍스트를 넘기고, 한 번 실행한 뒤 다시 잠재운다.[25][26]

    흐름은 다음 정도로 이해하면 충분하다.

    코드 53.3 하트비트 — 계속 도는 루프가 아니라 깨워서 일시키는 루프
    이슈 생성
  -> 큐에 등록
  -> 하트비트에서 담당 에이전트 깨우기
  -> 예산 / 작업공간 / 비밀값 / 스킬 준비
  -> 중복 실행 잠금으로 중복 작업 차단
  -> 어댑터 실행
  -> 로그와 결과를 남기고 대기 상태로 돌아감

    여기서 중요한 것은 중복 실행 잠금 이다. 같은 이슈를 여러 에이전트가 동시에 잡아 중복 비용을 쓰거나 서로 다른 결과를 덮어쓰는 일을 막는다. 조직형 패러다임에서 이슈는 단순 TODO가 아니라, 실행 권한과 감사 로그가 붙는 운영 단위다.

    3.4 운영 통제 — 알림이 아니라 차단

    Paperclip 사례에서 가장 봐야 할 지점은 거버넌스다. 대부분의 에이전트 프레임워크는 "리뷰 단계를 넣을 수 있다"에 가깝다. 반면 Paperclip은 특정 결정과 단계 전환을 시스템이 멈춰 세우는 규칙 으로 둔다.[26]

    대표적으로 두 가지가 있다.

    표 83.4 운영 통제 — 알림이 아니라 차단
    장치 역할 핵심
    승인 대기열 전략 승인, 에이전트 채용 같은 회사 수준 결정을 사람에게 올림 승인 전에는 다음 단계로 진행하지 않음
    실행 정책 이슈별 검토 / 승인 단계를 강제 에이전트가 리뷰를 "잊는" 일을 시스템이 막음

    이 차이가 조직형 패러다임의 핵심이다. 거버넌스가 문서나 운영자의 선의에만 있으면 바쁜 순간에 생략된다. 실행 경로 안에 들어간 거버넌스는 생략되기 전에 실행을 멈춘다.

    3.5 예산 — 비용도 운영 규칙이다

    에이전트 운영에서 비용은 사후 회계가 아니라 실행 규칙이 되어야 한다. Paperclip은 비용을 회사, 에이전트, 프로젝트, 목표, 이슈, 제공자, 모델, 월 단위 축으로 추적하고, 80%에서는 경고, 100%에서는 자동 일시정지를 수행한다.[26]

    이 메시지는 Paperclip에만 한정되지 않는다. 고객 데이터 수정, 외부 발행, 광고비 집행처럼 되돌리기 어려운 행동은 승인 한도와 비용 한도 가 실행 경로 안에 있어야 한다. 조직형 패러다임은 바로 이 지점을 프레임워크의 중심에 둔다.

    3.6 한계 — 조직형이 모델 품질을 보장하지는 않는다

    Paperclip이 제공하는 것은 운영 구조의 안전망이지, 모델 출력의 진실성 보장은 아니다.

    표 93.6 한계 — 조직형이 모델 품질을 보장하지는 않는다
    Paperclip이 강한 것 여전히 남는 문제
    누가 어떤 이슈를 맡았는지 추적 결과가 사실인지 자동 보장하지 않음
    승인 전 진행 차단 승인자가 대충 통과시키면 의미가 약해짐
    예산 초과 시 중단 한 번의 고비용 호출을 사전에 완전히 막지는 못함
    작업 로그와 감사 추적 사실관계·표현 리스크 판단은 별도 룰과 리뷰 필요

    따라서 결론은 "Paperclip을 쓰면 안전하다"가 아니다. 더 정확히는 조직형 시스템은 멈출 자리를 만들어 주지만, 무엇을 통과시킬지는 운영자가 설계해야 한다 다.

    이번 발표 뒤 별도 시연에서는 이론 전체를 반복하지 않는다. 대신 다음 네 가지를 화면에서 확인하면 충분하다.

    1. 목표가 이슈로 쪼개지는 방식
    2. 에이전트가 하트비트로 깨어나 작업하는 방식
    3. 승인 / 검토 단계에서 실행이 멈추는 방식
    4. 예산과 로그가 운영 화면에 남는 방식

    이 네 가지가 보이면, Paperclip은 "또 하나의 에이전트 프레임워크"가 아니라 조직형 운영 제어 계층의 한 구현 으로 이해할 수 있다.

    4. 정리 — 별도 시연과 질의응답으로 연결

    이 장의 한 줄 — 오늘의 결론은 특정 프레임워크를 고르는 것이 아니라, 자사 워크플로의 모양과 멈춤 규칙을 먼저 정의해야 한다는 것이다.

    4.1 오늘의 3개 메시지

    표 104.1 오늘의 3개 메시지
    메시지 의미
    코디네이션이 새 병목이다 모델 한 번의 답변보다 여러 호출·도구·사람 승인을 어떻게 조정하는지가 중요해졌다.
    오케스트레이션에는 유형이 있다 그래프형, 역할·핸드오프형, 조직형은 일을 나누고 멈추는 방식이 다르며, 스킬은 반복 기준을 공유하는 자산 계층이다.
    거버넌스는 실행 경로 안에 있어야 한다 외부 발행, 비용 집행, 고객 데이터 변경처럼 위험한 행동은 알림이 아니라 차단 규칙이 필요하다.

    4.2 별도 시연에서 확인할 것

    발표자는 별도로 준비한 quantsquard-company 시연에서 Paperclip식 조직형 운영을 보여준다. 본문 자료는 시연 절차서가 아니라 판단 프레임이므로, 시연에서는 다음 네 가지만 확인하면 된다.

    1. 목표가 어떤 단위의 이슈로 쪼개지는가
    2. 담당 에이전트가 어떤 컨텍스트를 받고 실행되는가
    3. 승인·리뷰 지점에서 실제로 실행이 멈추는가
    4. 로그와 비용 정보가 운영자가 다시 볼 수 있는 형태로 남는가

    4.3 질의응답 토론 시드

    질의응답에서는 Paperclip 기능 자체보다 커넥트브릭의 실제 업무 모양을 확인하는 쪽이 중요하다.

    표 114.3 질의응답 토론 시드
    질문 확인하려는 것
    현재 자동화하려는 업무는 고정 파이프라인인가, 역할 분업인가, 조직형 위임인가? 기본 패러다임
    사람이 반드시 승인해야 하는 지점은 어디인가? HITL과 차단 규칙
    비용 한도가 필요한 단위는 회사, 프로젝트, 고객, 작업 묶음 중 무엇인가? 예산 모델
    작성 기준·검수 규칙·반복 절차는 스킬로 관리할 만큼 자주 쓰이는가? 지식 자산화
    비개발 운영자가 볼 화면은 조직도형이어야 하는가, 시각 워크플로형이어야 하는가? 제품 UX 방향

    2회차에서는 이 질문들을 바탕으로 에이전트 작업 흐름과 오케스트레이션 구조 를 더 구체적으로 다룬다. 이번 회차의 오케스트레이션 유형은 프레임워크 선택의 기준이고, 다음 회차의 설계 패턴은 그 안에서 실제 작업 흐름을 구성하는 방법이다.
