    1. Weekly Digest — 에이전트 생태계 2026 5월

    1줄 thesis — 능력 경쟁은 끝났고, 코디네이션이 새 병목 이다.

    1.1 왜 지금 "에이전트 회사" 인가 — 큰 그림

    2024년 말부터 2025년까지의 흐름은 "모델 한 개의 능력을 어디까지 끌어올릴 수 있나" 의 경쟁이었다. Claude 4 / GPT-5o / Gemini 2.5 세대를 지나면서 단일 호출의 reasoning · tool use 품질이 충분히 올라간 결과, 병목은 모델 한 개의 IQ가 아니라 "여러 호출을 어떻게 조정하고, 어디까지 자율 실행을 맡길 것인가" 의 코디네이션 비용 으로 이동했다.

    LangChain의 State of Agent Engineering 2025/2026 설문(1,340명, 2025-11~12 수집)에서 응답자의 57%가 에이전트를 production에 투입 했다고 답했고, 1만 명 이상 대기업으로 좁히면 67%가 production 단계 다.[^langchain]

    이 맥락에서 "한 사람 + N개 에이전트로 운영되는 회사" 담론이 단순 밈을 넘어 실제 도구 카테고리로 굳어졌다. 2026-03-04 공개된 오픈소스 Paperclip 은 6주 만에 GitHub 53,000+ stars를 모았는데, 핵심은 "에이전트를 더 똑똑하게 만든다" 가 아니라 "에이전트들에게 직책·예산·승인 라인을 부여하고 조직도(org chart) 위에서 운영한다" 는 발상이다.[^paperclip-gh][^jimmysong] Gartner는 multi-agent 시스템 관련 문의가 2024 Q1 → 2025 Q2 +1,445% 증가 했다고 보고했고[^mlmastery], SK AX도 "2026년부터 10개 이상 에이전트가 협업하는 시스템이 보편화" 라는 국내 전망을 내놓았다.[^skax-multi] Paperclip은 이 흐름의 가장 가시적인 산출물 중 하나로 보는 것이 적절하다.

    1.2 메타 트렌드 5개 — 깊이판

    본 절은 사전 디지스트(digest.html)의 5 트렌드를 각각 한 단락 더 풀어서 정리한다. 디지스트가 30분 안에 훑는 사전 자료라면, 본 절은 세미나 후 다시 펴서 인용·근거를 확인하는 용도다.

    1.2.1 멀티에이전트 프레임워크의 패러다임 분화

    2025년까지 "에이전트 프레임워크" 라는 한 덩어리로 묶여 있던 영역이 2026년에는 패러다임별로 분명히 갈렸다. LangGraph (상태 그래프 + HITL 체크포인트, v0.4) / CrewAI (역할·프로세스 기반 crew, 엔터프라이즈 관측성 추가) / AutoGen v2 / AG2 (대화형 GroupChat, 1.0 GA) / OpenAI Agents SDK / Google ADK / Deep Agents (Anthropic 계열, skill 중심) 등이 각자 다른 멘탈 모델을 표방한다.[^pecollective][^turing]

    왜 중요한가 — "어떤 프레임워크를 쓰지?" 가 더 이상 취향 문제가 아니라 "우리 워크플로의 모양이 그래프냐, 역할극이냐, 대화냐, 회사냐" 라는 질문이 됐다. 본 리포트 2장에서 이 4분류를 본격적으로 다룬다.

    1.2.2 MCP(Model Context Protocol)의 사실상 표준화

    2024년 11월 Anthropic이 발표한 MCP가 18개월 만에 에이전트-도구 인터페이스의 사실상 표준 이 됐다. 공개 MCP 서버 레지스트리는 2025 Q1 1,200개 → 2026년 4월 9,400개+ 로 늘었고 (월간 +18% 성장), Claude / ChatGPT / Gemini / Cursor / Windsurf / Zed / JetBrains AI / Vercel AI SDK / OpenAI Agents SDK가 모두 MCP를 네이티브로 채택했다.[^digitalapplied][^mcp-roadmap]

    왜 중요한가 — 2025년까지의 통합은 "벤더별 plugin / function calling 스펙을 일일이 맞춰 짜기" 였는데, MCP 이후로는 "한 번 MCP 서버를 만들면 어떤 호스트에서든 붙는다" 가 됐다. F&B 마케팅 자동화 관점에서도 Shopify · Meta Ads · Instagram · GA4 · Slack 같은 외부 시스템을 MCP 서버 한 번 작성으로 모든 에이전트에 공유 가능. 단 2026년 현재 미해결 영역은 SSO 통합 auth · 감사 로그 · 게이트웨이 정책 으로, 엔터프라이즈 채택의 핵심 과제로 남아 있다.[^thenewstack]

    1.2.3 Agent Skills — 프롬프트 자산의 코드화

    Anthropic이 2025-12-18 Agent Skills 오픈 스펙 을 공개했다.[^anthropic-skills] 폴더 하나에 SKILL.md (YAML frontmatter + Markdown 지시문) + 보조 스크립트/리소스를 담는 단순 포맷이고, 핵심은 staged loading — 메타데이터만 부팅 시 읽고, 실제 호출될 때만 본문이 컨텍스트에 들어가서 토큰 비용을 잡는 구조다. 2026년 3월 시점 32개 도구 (Gemini CLI · JetBrains Junie · AWS Kiro · Block Goose · Cursor · OpenCode 등)가 동일한 SKILL.md를 읽는다.[^venturebeat]

    왜 중요한가 — 그동안 사내에 흩어져 있던 "ChatGPT 프롬프트 모음.docx" , "노션 프롬프트 라이브러리" 같은 비공식 자산이 버전 관리 가능한 코드 디렉토리 가 된다. F&B 마케팅이라면 브랜드 톤 매뉴얼 / 신메뉴 출시 카피 SOP / Meta Ads 캠페인 셋업 절차 를 각각 skill 폴더로 묶으면, 같은 자산을 Claude Code · Cursor · Paperclip의 모든 에이전트가 똑같이 호출 가능.

    1.2.4 Coding Agent의 성숙 + SDK 가격 재편

    Claude Code SDK가 2026년 3월 Claude Agent SDK 로 개명되며 "코드 전용" 프레임이 떨어져 나갔다. 같은 SDK 위에서 PowerPoint · Excel · Word · PDF 용 pre-built skill이 함께 제공되고, Cursor · Aider · Goose · OpenCode 같은 third-party 코딩 에이전트들이 같은 SKILL.md 포맷을 공유한다.[^anthropic-sdk] 한편 2026년 6월 15일부터 Claude Agent SDK · claude -p · GitHub Actions의 subscription 토큰이 별도 $200/월 크레딧 버킷으로 분리 되어, 헤비 유저의 실효 비용이 12~175배까지 오르는 정책 변경이 진행 중이다.[^releasebot]

    왜 중요한가 — "코딩 에이전트 = 개발자 전용" 의 구도가 깨지고 있다. Excel · PDF · PPT skill을 가진 동일 SDK가 마케팅 · 기획 · 운영 시나리오로 들어오는 중이고, 동시에 가격 모델이 "API 종량제" 로 회귀하면서 운영 비용을 처음부터 설계 변수로 두는 cost-aware 아키텍처 가 필수가 됐다.

    1.2.5 관찰성·평가의 표준화 — OTel + LangSmith 라인

    2026년 3월 LangSmith가 OpenTelemetry full support를 추가하면서, Laminar · Langfuse · LangSmith · Phoenix가 모두 OTLP를 공통 수신 포맷 으로 받게 됐다. 즉 에이전트 trace가 벤더 종속 없이 이식 가능해진 첫 해다.[^braintrust][^agentmarketcap] LangChain 설문 기준 production 운영 팀의 89%가 observability를 도입 했고, 62%는 단계별 step · tool call 단위 trace를 본다.

    왜 중요한가 — 멀티 에이전트가 늘어날수록 "왜 이 캠페인 카피가 이렇게 나왔는지" 의 사후 추적성이 production의 사활을 가른다. LangChain 설문에서 production 진입을 가로막는 1위 이유가 "quality" (32%) 였는데, 관찰성 없는 품질 개선은 불가능하므로 OTel은 사실상 진입 요건이 되고 있다.

    1.3 F&B 마케팅 자동화 관점 — 시드 3개

    본격 적용 논의는 5장 — 여기선 시드만 던진다.

    1. 조직형 오케스트레이션의 자연스러움 — Paperclip식 org-chart + 예산·승인 라인 모델은 F&B 마케팅의 캠페인 단위 워크플로 + 브랜드 매니저 승인 구조와 mental model이 가장 잘 맞는다 (가설, Q&A에서 검증).
    2. MCP 서버 = 통합 ROI 최대 영역 — Meta Ads · GA4 · 인스타 DM · Shopify · POS · 배달앱을 MCP 서버로 한 번 감싸면, 카피라이팅 · 캠페인 분석 · CS 에이전트가 모두 같은 도구를 쓸 수 있다.
    3. Brand 톤 = SKILL.md 로 자산화 — 브랜드 가이드라인 · 금지어 · 페르소나를 Agent Skill로 패키징하면 Claude · Cursor · Paperclip 어디서든 동일 톤이 강제된다 — 흩어진 프롬프트 사이로 새는 일관성 문제의 구조적 해법.

    2. 프레임워크는 패러다임이다 — 4-Way 분류

    이 장의 한 줄 — 2026년의 에이전트 프레임워크 선택은 "어느 라이브러리가 좋은가" 가 아니라 "우리 워크플로의 모양이 무엇과 닮았는가" 를 묻는 문제다.

    1장에서 본 것처럼 단일 모델 능력의 한계 효용이 떨어진 결과, 2025년 한 덩어리로 묶여 있던 "에이전트 프레임워크" 카테고리는 2026년에 분명한 4개 패러다임으로 갈렸다. 본 장은 이를 그래프형 / 역할극형 / skill 중심 / 조직형 의 4-way로 정리한다. 이 분류는 작성자(송태영)의 정리이며 학술 분류가 아니다 — Turing(2026), pecollective(2026)의 6~8개 프레임워크 비교를 mental model 단위 로 묶어낸 발표용 프레임이다.

    2.1 그래프형 (LangGraph)

    Mental model

    그래프형(graph-based) 의 멘탈 모델은 상태 그래프(state graph) + 노드(node) + 엣지(edge) + 체크포인트(checkpoint) 다. 워크플로를 노드(에이전트 또는 도구 호출 한 단계)와 엣지(다음 노드로 가는 조건부 전이)로 명시적으로 그리고, 각 노드의 입출력은 공유 state 객체에 누적된다. LangGraph의 차별점은 노드 사이에 HITL(human-in-the-loop) 체크포인트 를 1급 시민으로 끼워 넣을 수 있다는 점 — 특정 엣지에서 실행을 멈추고 사람 승인을 기다린 뒤 재개하는 패턴이 SDK 수준에서 지원된다.

    구조 예시 (의사코드)

    from langgraph.graph import StateGraph, END

graph = StateGraph(CampaignState)
graph.add_node("research", research_agent)
graph.add_node("draft", writer_agent)
graph.add_node("brand_review", human_approval)   # HITL 체크포인트
graph.add_node("publish", publisher_agent)

graph.add_edge("research", "draft")
graph.add_edge("draft", "brand_review")
graph.add_conditional_edges(
    "brand_review",
    lambda s: "publish" if s.approved else "draft",  # 반려 시 draft 재실행
)
graph.add_edge("publish", END)

    잘 맞는 워크플로

    분기가 결정적(deterministic) 이고 단계 수가 미리 알려진 워크플로 — 예: 리서치 → 초안 → 검수 → 발행 처럼 노드 개수와 순서가 거의 고정된 파이프라인. 분기 조건을 코드로 명시할 수 있고, HITL 체크포인트가 자연스러운 자리에 들어가는 작업이라면 그래프형이 가장 추적성이 높다. 반대로, 단계 수 자체가 LLM의 판단에 따라 가변적이거나 발산적 토론이 필요한 작업에는 그래프가 폭발한다.

    2.2 역할극형 (CrewAI, AutoGen)

    Mental model

    역할극형(role-playing) 의 멘탈 모델은 역할(role) + 대화(conversation) + 협상(negotiation) 이다. 각 에이전트는 직책(researcher / writer / critic 등)과 페르소나를 받고, 작업은 그들끼리 대화하는 과정 에서 산출된다. CrewAI는 이를 "process 기반 crew" 로 정형화하고, AutoGen / AG2는 GroupChat 추상으로 다자 대화를 1급 시민으로 만든다. 흐름이 코드로 미리 그려지지 않고 — 누가 언제 발언하는지는 manager 또는 termination 조건이 런타임에 결정한다.

    구조 예시 (YAML, CrewAI 스타일)

    crew:
  agents:
    - role: trend_researcher
      goal: 한국 카페 신메뉴 트렌드 5건 발굴
    - role: copywriter
      goal: 발굴 트렌드 기반 인스타 릴스 카피 3안 작성
    - role: brand_critic
      goal: 브랜드 톤 위반 항목 지적 + 반려/통과 판정
  process: sequential   # 또는 hierarchical (manager 지정)
  tasks:
    - description: 5개 트렌드 리서치
      agent: trend_researcher
    - description: 카피 3안 → critic 피드백 → 수정
      agents: [copywriter, brand_critic]

    잘 맞는 워크플로

    발산적 브레인스토밍, 다관점 검토, 합의 형성 이 본질인 작업 — 예: 캠페인 컨셉 발굴, 카피 A/B 후보 생성, 다관점 리뷰. 단계가 미리 정해져 있지 않고 "누가 무엇을 말하는가" 의 페르소나가 산출물 품질을 좌우하는 영역. 반대로, deliverable의 형태와 승인 라인이 명확히 고정된 운영 워크플로에는 대화가 과한 표현력이 된다 (수렴이 느리거나 무한 핑퐁이 발생).

    2.3 Skill 중심 (Deep Agents, Claude Agent SDK)

    Mental model

    Skill 중심(skill-based) 의 멘탈 모델은 도구 라이브러리(tool library) + 메인 루프(main loop) + 스테이지드 로딩(staged loading) 이다. 에이전트 1대가 큰 메인 루프를 돌리고, 작업에 필요한 능력은 사전에 작성된 SKILL.md 폴더(YAML frontmatter + 절차 지시문 + 보조 스크립트)에서 동적으로 꺼내 쓴다. 핵심은 staged loading — 메타데이터만 부팅 시 로드되고, 본문은 실제 호출 시점에만 컨텍스트에 올라가서 토큰 비용을 잡는다 (1장 §1.2.3). 그래프나 대화가 흐름의 표현 이라면, skill 중심은 능력의 모듈화 다.

    구조 예시 (디렉토리)

    .claude/skills/
├── brand-tone/
│   ├── SKILL.md           # 메타데이터 + 호출 트리거
│   ├── guidelines.md      # 본문 (호출 시 로드)
│   └── forbidden.json
├── meta-ads-campaign/
│   ├── SKILL.md
│   └── setup.py           # 보조 스크립트
└── instagram-reels/
    └── SKILL.md

    # SKILL.md frontmatter 예시
---
name: brand-tone
description: 커넥트브릭 브랜드 톤·금지어·페르소나 강제
triggers: [copy_review, draft_writing]
---

    잘 맞는 워크플로

    코딩, 문서 작성, RAG-heavy 작업 — 단일 에이전트가 광범위한 도구·자산을 활용해 산출물을 만들지만, 호출되는 능력의 집합은 작업마다 달라지는 영역. 사내 자산(브랜드 톤, 카피 SOP, 캠페인 셋업 절차)이 코드 리포지토리에 버전 관리되어야 할 만큼 누적되어 있다면 강력하다. 반대로, 여러 에이전트가 병렬로 협업하면서 승인·예산을 공유해야 하는 운영 워크플로 에는 단일 메인 루프가 병목이 된다.

    2.4 조직형 (Paperclip)

    Mental model

    조직형(organization-based) 의 멘탈 모델은 회사(company) — 조직도(org chart) + 목표(goal) + 예산(budget) + 거버넌스(governance) 다. 에이전트는 "역할" 이 아니라 직책(role) + 보고 라인(reporting line) + 예산 한도(budget cap) + 승인 권한(approval scope) 을 가진 직원 으로 모델링되고, 일감은 회의·메시지가 아니라 이슈(issue) / 태스크(task) / 골(goal) 이라는 deliverable 단위로 흘러간다. 결정적 차별점은 거버넌스가 런타임 강제(runtime-enforced) 라는 점 — 승인 큐에 걸린 strategy는 단순 알림이 아니라 미승인 시 하위 태스크 진행 자체를 시스템이 막고, 예산 80% soft / 100% hard-stop이 8개 차원으로 추적되어 자동 pause를 건다.

    Deep dive 안내

    본 패러다임의 8 서브시스템, heartbeat 루프, executionPolicy, approval queue, 8차원 budget 추적의 구체 메커니즘은 본 리포트 3장 (Paperclip 심층 분석) 에서 별도로 다룬다. 본 장에서는 4분류 안에서의 위치 — "가장 governance-first" 인 패러다임 — 만 명확히 해 두는 것으로 충분하다.

    F&B 마케팅에 왜 조직형이 자연스러운가 (가설)

    F&B 마케팅 자동화의 구조적 특징 을 단순화하면 다음 4가지다.

    1. 캠페인 단위 deliverable — "신메뉴 출시 캠페인 5월호" 처럼 결과물의 단위가 명확하다 (이슈에 가까움, 노드 시퀀스에 가깝지 않음).
    2. 브랜드 매니저 승인 라인 — 카피·이미지가 외부 채널로 나가기 전 사람이 반드시 들여다본다 (단순 알림이 아닌 런타임 차단 이 필요).
    3. 채널·매체별 예산 한도 — Meta Ads, 인플루언서, 시즌별 한도가 명확히 정해져 있고, 한도 초과는 조직 정책 위반 이다 (시스템이 강제해야 함).
    4. 여러 에이전트의 동시 진행 — 카피라이팅 · 디자인 · 캠페인 분석 · CS가 병렬로 돌면서도 같은 브랜드 가이드 · 같은 예산 풀을 공유해야 한다.

    이 4가지를 어떤 패러다임의 mental model이 1:1로 받아내는가 를 물어보면, 그래프형은 1번에는 강하지만 2~4번이 외부 wrapper가 되고, 역할극형은 4번을 자연스럽게 받지만 2번·3번이 대화 합의 로 흐려진다. Skill 중심은 1번 단일 산출물에는 강하지만 4번 병렬 협업이 단일 메인 루프 안에 갇힌다. 조직형은 4가지가 각각 — 이슈 / approval queue / budget cap / org chart 로 1차 시민이다.

    이것이 본 세미나의 핵심 가설이다 — F&B 마케팅의 도메인 구조와 조직형 mental model 사이의 형태 일치(shape match) 가 다른 3 패러다임 대비 자연스럽다. 단, 이는 작성자(송태영)의 가설이며 단정이 아니다. 본 세미나 Q&A에서 청중(커넥트브릭 개발팀)이 가진 실제 워크플로 모양 을 들어 검증·반박하는 것이 목적이다.

    본 분류의 위상 — 작성자 정리, 학술 분류 아님

    본 4-way 분류는 발표용 mental model 프레임이며, 학술적 taxonomy가 아니다. Turing(2026)·pecollective(2026)·Morphllm(2026) 등은 6~8개 프레임워크를 기능 매트릭스 로 비교하고, Andrew Ng(2024)의 4 design patterns(reflection / tool use / planning / multi-agent)은 흐름 패턴 차원의 분류다. 본 4-way는 그중에서 "우리 워크플로의 모양과 mental model의 형태 일치" 라는 단일 축으로 단순화한 것이며, 다른 축(governance / 비용 / 관찰성)을 같이 보면 다른 그림이 나온다 — 본 리포트 3장과 5장에서 이 다른 축들을 보강한다.

    3. Paperclip 심층 — 아키텍처 + 거버넌스

    2장에서 본 4 패러다임 중, "조직형(organizational)" 의 대표 케이스 Paperclip을 한 층 더 들어간다. 본 장의 목적은 두 가지다 — (1) 8개 서브시스템 위에서 하트비트 루프(heartbeat loop) 가 어떻게 일을 도는지를 코드 레벨 직전까지 그려보고, (2) 거버넌스(governance)가 단순 알림이 아니라 런타임이 강제하는 차단(runtime-enforced gating) 으로 동작한다는 점을 보인다.

    3.1 한 줄 정의 + 슬로건

    Paperclip은 "AI 에이전트 팀을 회사처럼 운영하는" 오픈소스 오케스트레이션 플랫폼(orchestration platform) 이다. Node.js 서버 + React UI + PostgreSQL 위에 하트비트(heartbeat) 기반 작업 큐와 8개 서브시스템을 얹어 외부 에이전트 런타임(Claude Code, Codex, CLI, HTTP, Plugin)을 통합 관제한다(research/01 §1).

    제작자의 공식 표현이 본 장의 한 줄 메시지를 가장 잘 요약한다(research/02 §1).

    "If OpenClaw is an employee, Paperclip is the company."

    곧 Paperclip은 "더 똑똑한 한 명의 에이전트" 를 만드는 도구가 아니라, "여러 에이전트가 일하는 회사라는 컨테이너" 를 제공하는 도구다. 이 프레임이 다른 패러다임과의 차이를 가른다 (확인 — research/01, research/02 공통 진술).

    3.2 8 서브시스템 아키텍처

    Paperclip의 시스템 다이어그램은 React UI ↔ Node.js API 서버를 중심으로 8개 서브시스템이 PostgreSQL과 외부 어댑터를 끼고 도는 구조다(research/01 §2).

    React UI ──REST/WS── Node.js API 서버 ── 8개 서브시스템
                          │
            ┌─────────────┼────────────────┐
       PostgreSQL    외부 에이전트 어댑터    Plugins
       (issues,      (Claude Code / Codex /  (out-of-process
        activity,     CLI / HTTP / Plugin)    workers)
        cost, secrets)

    8개 서브시스템은 다음과 같다(research/01 §2).

    # 서브시스템 역할
    ① Identity & Access board user / member / agent 식별과 권한
    ② Org Chart & Agents 조직도, 에이전트 정의(role, reportsTo, budget, adapter)
    ③ Work & Task Goal → Issue 트리, blocker, assignee, work products
    ④ Heartbeat Execution DB-backed wakeup 큐 + atomic checkout + adapter 호출 (핵심 루프)
    ⑤ Workspaces & Runtime git worktree 기반 격리 작업 공간
    ⑥ Governance & Approvals approval queue + execution policy
    ⑦ Budget & Cost Control 8차원 cost 추적 + 80% / 100% threshold
    ⑧ Routines & Schedules cron / webhook / API 트리거

    데이터 모델의 골격은 Company → Project → Goal → Issue 4계층이며, Issue 한 건이 "원자 작업 단위(atomic work unit)" 다(research/01 §3).

    Company (격리 단위, deployment당 무제한, export/import 가능)
 ├── Board Users / Members
 ├── Agents (role, title, reportsTo, budget, adapter)
 ├── Projects → Workspaces (isolated git worktree)
 └── Goals (mission tree)
       └── Issues (= 티켓, 원자 작업 단위)
            ├── company_id / project_id / goal_id / parent_id
            ├── blockers[] (의존성), assignee (Agent)
            ├── execution_lock (atomic checkout)
            ├── comments, attachments, work_products
            └── activity[] (immutable audit log)

    여기서 핵심 원칙은 모델/에이전트 불가지론(model-agnostic) 이다 — "If it can receive a heartbeat, it's hired" (research/01 §2 인용).

    3.3 Heartbeat 루프 — 핵심 실행 모델

    Paperclip의 모든 일은 하트비트 한 박자(one heartbeat) 위에서 도는데, 이는 다른 패러다임의 "continuous agent loop" 와 결정적으로 다르다. 한 박자의 라이프사이클은 다음과 같다(research/01 §4).

    1. Issue 생성 (수동 / Routine cron·webhook·API / 다른 에이전트 위임)
   → company / project / goal / parent 링크 부여 (goal ancestry 결정)
2. DB-backed wakeup queue에 enqueue (coalescing으로 중복 병합)
3. 하트비트 도착 → Budget check → Workspace resolve (git worktree)
   → Secret injection (필요 시만) → Skill loading → Adapter 호출
4. Atomic checkout — 실행 lock ("no double-work, no runaway spend")
5. 에이전트 실행 → 구조화 로그 / cost 이벤트 / 세션 상태 / 감사로그
6. work products 첨부, issue 상태 갱신, (옵션) Governance 승인 게이트

    세 가지 의미가 두드러진다.

    첫째, atomic checkout + execution lock. 한 issue는 한 번에 한 에이전트만 잡는다 — "no double-work, no runaway spend" 가 README의 직접 표현이다(research/01 §4). 동일 issue를 두 에이전트가 동시에 가져가 같은 비용을 두 번 태우는 사고를 시스템 레벨에서 차단한다.

    둘째, goal ancestry로 컨텍스트 상속. 에이전트는 "왜 이 일을 하는가" 를 자기 정의(role/budget/permissions) + 조직 컨텍스트(reporting line/회사 미션) + 작업 컨텍스트(issue + parent + blockers + 첨부) + 세션 컨텍스트(이전 하트비트 상태)를 함께 받아 안다(research/01 §4).

    Company Mission → Project Goal → Parent Issue → Sub-issue / Agent

    셋째, 세션 영속성(session persistence). 하트비트 사이에 에이전트는 죽는 게 아니라 "잠든다" — 다음 하트비트에서 DB에 적재된 상태를 그대로 이어 받는다("Persistent agent state. Agents resume the same task context across heartbeats instead of restarting from scratch." research/01 §6 인용). 큐 자체도 DB-backed라 서버 재시작 후 복원된다.

    3.4 Org Chart + 위임 모델

    조직도는 엄격한 트리(strict hierarchy) 다(research/02 §2.1).

    • 모든 에이전트는 reportsTo 필드를 갖고, 정확히 한 명의 매니저 에게 보고한다. 사이클 금지(acyclic), 단일 부모.
    • 루트는 CEO 에이전트 — CEO만 사람(board operator)에게 직접 보고한다.
    • 각 에이전트는 자신의 chainOfCommand 를 갖고, escalation(블로커 시 매니저로 reassign) · delegation(매니저가 reports에게 subtask 생성) · visibility(매니저가 reports 작업 조회) 세 용도로 쓴다.
    • 교차팀 작업(cross-team work)은 허용되지만, 보고 라인 밖의 태스크를 받은 에이전트는 그것을 cancel할 수 없고 자기 매니저에게 reassign해야 한다 (research/02 §2.1).

    에이전트 한 명의 정의는 6개 필드로 압축된다(research/02 §2.2).

    필드 예
    Name "CEO", "Frontend Engineer"
    Role (string slug) ceo, cto, manager, engineer, researcher 등
    Reports to 매니저 에이전트 ID
    Adapter type + config claude_local, codex_local, opencode_local, openclaw_gateway, http, process
    Capabilities 짧은 자연어 설명
    Budget 월간 cent 단위 한도

    여기서 중요한 관찰은 role이 enum이 아니라 자유 문자열 슬러그 + capabilities 자연어 조합 이라는 점이다 — Content Strategist / Editor / Publisher 같은 마케팅 특화 템플릿은 (현시점) 기본 제공이 아니라 사용자가 명명한다(research/02 §2.2).

    3.4.1 Hire-on-Demand 패턴

    구조 자체는 정적(트리, 단일 부모, 사이클 금지)이지만 인원 구성은 동적 이다 — CEO가 작업이 더 필요해지면 hire_agent approval을 보드(사람)에게 제출 → 승인 시 새 에이전트가 트리에 붙는다. 이것을 Hire-on-Demand 패턴으로 부른다(research/02 §2.3).

    위임 라이프사이클은 docs가 다음 한 블록으로 정리하고 있다(research/02 §3.1).

    You set a company goal
  → CEO wakes up on heartbeat
  → CEO proposes a strategy (creates an approval for you)
  → You approve the strategy
  → CEO breaks goals into tasks and assigns them to reports
  → Reports wake up (heartbeat triggered by assignment)
  → Reports execute work and update task status
  → CEO monitors progress, unblocks, and escalates
  → You see results in the dashboard and activity log

    핵심 불변량(invariant)은 한 줄이다 — "Every task traces back to the goal through a parent hierarchy" (research/02 §3.1 인용).

    3.5 거버넌스 — 런타임 강제

    본 장의 메시지 중 가장 결정적인 부분이다. Paperclip의 거버넌스는 두 축이 런타임에서 작동 한다 — (A) 회사 레벨의 Approval Queue, (B) 태스크 레벨의 Execution Policy (research/02 §6).

    3.5.1 (A) Approval Queue — 회사 레벨

    hire_agent 와 ceo_strategy 두 가지가 명시적 승인 타입이다(research/02 §6.1).

    pending → approved
       → rejected
       → revision_requested → resubmitted → pending

    운영자는 Approvals 페이지에서 (1) 요청자 / 사유, (2) 연관 이슈, (3) 전체 payload(예: 신규 에이전트 config 전체) 를 보고 결정한다. 승인 전엔 CEO가 태스크를 in_progress로 못 옮긴다 (research/02 §3.2). 곧 미승인은 단순 알림이 아니라 진행 자체의 차단이다.

    3.5.2 (B) Execution Policy — 태스크 레벨

    이슈마다 선택적으로 붙는 executionPolicy 객체로, 세 layer를 조합한다(research/02 §6.1).

    Layer 목적 스코프
    Comment required 모든 에이전트 run은 이슈에 코멘트를 남겨야 함 런타임 불변량(항상 on)
    Review stage 리뷰어가 품질/정확성 확인, 변경 요청 가능 이슈별 옵션
    Approval stage 매니저/스테이크홀더 최종 sign-off 이슈별 옵션

    조합 가능 — review만 / approval만 / review→approval 순차 / 둘 다 없이 comment-only(research/02 §6.1). 런타임이 강제 하는 게 핵심이다 — 에이전트가 "리뷰 잊을" 가능성을 시스템이 차단한다.

    3.5.3 보드 오버라이드 (Board Override Powers)

    운영자(보드)는 언제든 다음을 할 수 있다(research/02 §6.2).

    • 에이전트 pause / resume / terminate(영구, 비가역)
    • 어떤 태스크든 다른 에이전트로 reassign
    • budget 한도 override
    • 승인 플로우를 우회해 에이전트 직접 생성

    곧 자율 실행 위에 사람이 언제든 잡아끄는 비대칭 권한이 존재한다. 거버넌스의 안전망이 "논리적 강제 + 인간 비대칭 오버라이드" 의 이중 구조다.

    3.6 예산 거버넌스

    비용은 8개 차원 으로 추적된다 — company · agent · project · goal · issue · provider · model · (월별 UTC 집계)(research/02 §4.1). 각 하트비트가 cost event를 보고하며, 필드는 provider / model / inputTokens / outputTokens / costInCents 다.

    정책은 단순 명료한 두 임계다(research/02 §4.2).

    Threshold Action
    80% Soft alert — agent is warned to focus on critical tasks only
    100% Hard stop — agent is auto-paused, no more heartbeats
    • 단위: cent 단위 USD (예: 회사 예산 100,000 cents = $1,000/월; 에이전트 5,000 cents = $50/월).
    • 100% 도달 시 에이전트 자동 paused + 큐잉된 작업도 자동 cancel.
    • 복구는 budget을 올리거나 다음 캘린더 월(UTC) 도래까지 대기.
    • 운영자는 budget을 override할 권한이 있다.

    3.6.1 단점 — 일/분 단위 budget 없음

    여기서 한 가지 한계가 분명하다. 일 단위 / 분 단위 budget은 존재하지 않는다 — 월간(UTC) 단위만 있다 (research/02 §4.2, §9.3-1). 단기 burst 컨트롤이 약하다는 뜻이다. 단일 하트비트 내 토큰 폭발은 직후에야 차단되며, "burst" 한 번의 손실은 막지 못한다(추정 — research/02 §8).

    운영 측면에선 다음 보완이 필요하다(권고, research/02 §9.3-1).

    • 자체 사전 제한(adapter 단에서 per-call max_tokens 등) 병행
    • 일간 alert를 routine으로 합성(예: 매일 09:00 회사 spend 점검 routine)

    3.7 운영 위험 vs Paperclip 안전망

    운영 의사결정 관점에서 보면, Paperclip이 직접 막아 주는 것 과 여전히 사람이 책임져야 하는 것 을 분리하는 표가 가장 유용하다(research/02 §8 압축).

    위험 Paperclip 대응 잔여 위험
    비용 폭주 80% soft / 100% hard-stop, 8차원 추적 일/분 budget 없음 → 단기 burst (확인)
    중복 작업 / 경쟁 조건 이슈 atomic checkout + execution lock —
    컨텍스트 손실 / 세션 리셋 persistent agent state, 하트비트 간 task 컨텍스트 유지 모델 context window 한계는 별개
    에이전트 무한 루프 heartbeat 모델 자체가 wake → act → sleep + budget hard-stop 한 heartbeat 내부 루프는 adapter 책임
    무단 결정 (전략·채용) CEO strategy / hire 둘 다 board approval 필수 "통째 승인" 패턴에 빠지면 거버넌스 무력화
    품질 누락 (리뷰 스킵) execution policy review / approval stage 런타임 강제 리뷰어가 다른 에이전트면 환각 단계 전파 가능
    감사 추적성 모든 mutation activity log + tool-call tracing 로그 신뢰성은 OK, 모델 출력 진실성은 별개
    할루시네이션 / 사실 오류 직접 차단 메커니즘 없음 — review stage 사람 강제만 가능 본질적 잔여 위험 (확인)
    브랜드 / 평판 리스크 가시성·중단 권한만 제공 F&B처럼 톤이 결정적인 도메인은 reviewer-of-record 필수 (추정)
    외부 비용 (SaaS·인프라) 토큰/모델 비용만 추적 별도 회계 필요
    모델 다운 / 장애 "Recovery handles orphaned runs automatically" 어디까지인지 docs 불명 (검증 필요)

    표의 메시지를 한 줄로 압축하면 — Paperclip은 "조직 운영의 구조적 안전망" 을 제공하지만, "모델 출력의 진실성" 은 보장하지 않는다. 후자는 reviewer-of-record(사람 또는 검증 에이전트)를 execution policy로 강제하는 책임이 운영자에게 남아 있다.

    3.8 "왜 조직형이 다른가" 결론 (T3 메시지)

    본 장의 결론을 본 세미나의 T3 메시지로 응축하면 한 줄이다 — 거버넌스가 런타임 강제(runtime-enforced)여야 한다 (spec §2.3).

    이 명제가 다른 패러다임과 결정적으로 갈리는 지점은 다음 셋이다(research/02 §6, §8, spec §2.3 종합).

    1. 승인은 알림이 아니라 차단이다. hire_agent / ceo_strategy approval queue는 단순 알림이 아니라 미승인 시 태스크 진행 자체를 막는다(research/02 §3.2, §6.1). 다른 패러다임은 "approve 함수를 호출 안 하면 그냥 안 부르는" 수준에 가깝다 — 즉 거버넌스가 사용자의 자율 규율에 맡겨진다.
    2. 품질 게이트는 이슈 수준에서 작동한다. executionPolicy 의 review/approval stage가 이슈 수준에서 작동하므로, "에이전트가 잊을" 가능성을 시스템이 차단한다(research/02 §6.1). 코드형(skill-centric) 패러다임은 main loop 안의 tool call로 review를 흉내 낼 수 있지만, 그건 "에이전트가 자발적으로 호출했을 때만" 작동한다.
    3. 예산은 자동 pause를 동반한다. 80% soft / 100% hard-stop이 8개 차원으로 추적되어 자동 pause + 큐 cancel까지 간다(research/02 §4.2). 다른 패러다임의 cost tracking은 "기록" 까지 가지만 "자동 중단" 까지 가는 경우는 드물다.

    곧 다른 세 패러다임이 "어떻게 일하느냐(workflow)" 의 메탈모델인 데 비해, 조직형(Paperclip)은 "어떻게 일하지 않게 하느냐(stop rules)" 의 메탈모델을 시스템에 박아 두었다. F&B 마케팅처럼 브랜드 톤 · 법규 · 예산 한도 가 결정적인 도메인에서는 후자가 결정적 차별점이 된다(추정 — 가설은 2장 T2 토론으로 검증).

    다만 단정은 아니다. "런타임 강제" 의 이점은 운영자가 그 거버넌스를 진지하게 운용할 때만 살아난다 — "통째 승인" 패턴에 빠지면 형식만 남는다(research/02 §8 잔여 위험). Paperclip의 약속은 "강제할 수 있는 자리" 를 마련해 둔 것이지, "강제가 저절로 일어나는 것" 은 아니다.

    4. 라이브 데모 워크스루

    본 장은 세미나 중 20분간 진행되는 라이브 데모의 시나리오와 시연 항목을 정리한다. 데모 환경은 사전에 셋업된 Paperclip 로컬 인스턴스를 사용한다.

    4.1 시나리오 정의 (Nevo David 파이프라인 모방)

    데모는 Nevo David의 5-skill 마케팅 파이프라인을 Paperclip의 org chart 위로 재구성한 reference architecture를 따른다 (spec §4.1).

    [Goal] "이번 주 인스타 릴스 3개 발행"
  ↓
CEO 에이전트 → Strategy proposal (사람 승인)
  ↓
Content Strategist → 5개 후보 topic 제안 (Issue로 생성)
  ↓
Writer → 승인된 1건 스크립트 작성 (시연 중)
  ↓
Editor → 리뷰 stage (execution policy 작동 시현)
  ↓
Publisher → Postiz upload + 다채널 예약 (mock 처리)

    정정 노트 — research/03 §0에서 확인했듯 Nevo David는 Paperclip의 실제 사용자가 아니라 Postiz(오픈소스 소셜 스케줄러)와 agent-media(UGC 비디오 CLI)의 창업자다. 그의 파이프라인은 Claude Code skills + Postiz CLI/MCP + agent-media MCP + n8n 조합으로 돌아간다. 본 데모는 "Nevo가 Paperclip을 쓴다"가 아니라 그의 도구 스택을 Paperclip org chart 메타포로 묶은 reference architecture 임을 발표 도입부에서 명시적으로 프레이밍한다 (spec §7 위험표 "Nevo 정정 인용 위험" 대응).

    4.2 사전 셋업 상태 (데모 시작 전 화면)

    라이브 시연의 첫 화면은 다음 상태로 고정한다.

    • 회사: Demo Marketing Co (단일 인스턴스)
    • CEO 에이전트: 1명, adapter는 Claude Code
    • 하위 에이전트: 미할당 (Strategy 승인 후 자동 생성되는 흐름을 보여주기 위함)
    • Budget: 회사 단위 80% 직전 상태로 인위적 셋업 — 6번 시연 항목에서 즉시 트리거 가능하도록 (spec §4.3 결정)
    • Activity log: empty
    • Goal: 미할당 (데모 중 운영자가 등록)
    • Approval queue: 비어있음

    이 정적 frame은 청중에게 "지금부터 모든 이벤트가 라이브"라는 신호를 준다.

    4.3 6 시연 항목 워크스루

    각 항목은 spec §4.2 표를 따른다.

    1. Approval queue UI 조작 (2~3분) — 운영자(human-in-the-loop) 권한으로 로그인된 화면에서 Approval queue 패널을 연다. 비어있는 상태에서 시작해, 다음 단계에서 자동으로 항목이 쌓이는 흐름을 예고. 운영자 권한이 회사 전체 거버넌스 게이트 역할임을 한 문장 설명.

    2. CEO Strategy 승인 → Subtask 자동 생성 (3~4분) — Goal 입력란에 "이번 주 인스타 릴스 3개 발행" 을 등록. CEO가 heartbeat 루프에서 Strategy proposal을 만들어 queue에 올리고, 발표자가 승인하면 Content Strategist / Writer / Editor / Publisher 4개 Subtask가 자동 생성·위임된다. 메시지 T3 "거버넌스 런타임 강제"의 첫 증거.

    3. Writer 에이전트 실행 (heartbeat → execution lock) (3~4분) — Writer detail view에서 heartbeat 카운터 증가와 execution lock 점유 모습을 노출. 동일 이슈에 다른 에이전트가 끼어들지 못하는 mutual-exclusion이 시각적으로 드러난다. Activity log에 LLM 호출 + skill 호출이 실시간으로 append.

    4. Execution policy review stage 작동 (2~3분) — Writer draft 완료 시 이슈가 자동으로 review stage로 전환되고 Editor가 다음 heartbeat에서 픽업. 이 stage 전환은 prompt가 아닌 executionPolicy 설정으로 강제되어 에이전트가 "잊을" 가능성이 차단됨 — T3의 직접 증거.

    5. Activity log walk-through (2~3분) — 회사 단위 Activity log에서 1~4번 모든 이벤트(승인 / Subtask 생성 / heartbeat / LLM·skill 호출 / stage 전환)가 시간순으로 쌓인 모습을 보여준다. 감사 추적(audit trail)의 완결성. F&B 도메인의 위생/원산지/광고법 검증 시 필수가 될 자산이라는 한 줄 코멘트.

    6. Budget 알림 (80%/100% 시뮬레이션) (2~3분) — 사전 셋업이 80% 직전이었으므로 직전 LLM 비용이 누적되면 즉시 80% soft 알림 발생. 발표자가 한도를 더 낮춰 100% hard-stop을 트리거하면 진행 중 Subtask 자동 pause + 대기 큐 cancel. 8개 차원(company/agent/project/goal/issue/provider/model/UTC월) 추적의 의미 한 줄 정리.

    합계: 약 14~20분. spec §3 어젠다 20분 슬롯 내. 시간 압박 시 6번 단축으로 약 5분 절감 가능 (spec §4.2 단축 옵션).

    4.4 실제 시연 시 주의점 / Q&A 예상 질문

    상급 청중에서 나올 가능성이 높은 5개 질문에 발표자 시드 답변을 미리 준비한다.

    Q1. "Claude Code adapter 토큰 비용은?" — 데모 1회 기준 추정 1~3달러. heartbeat 루프가 자주 돌아 누적이 빠르므로 회사 단위 budget 한도가 필수다 (본 데모 6번 시연이 그 답이다).

    Q2. "Production에서도 단일 인스턴스로 운영 가능한가?" — 현재 Paperclip은 single-process 가정의 로컬 우선 도구. 멀티 인스턴스/HA 구성은 공식 가이드 부재. Production 적용 전에 dogfood로 운영 한계를 직접 확인하는 게 안전 (작성자 견해).

    Q3. "한국어 prompt가 영어보다 비싼가?" — Claude 계열은 한국어 토큰 효율이 영어 대비 약 1.5~2배 비싼 편으로 알려져 있다 (모델·버전 의존, 정확 수치는 검증 권장). budget 추정 시 한국어 도메인엔 이 계수를 반영해야 한다.

    Q4. "회사 1개 안에 여러 클라이언트(브랜드)를 분리 가능한가?" — Paperclip은 회사(company) 단위 격리가 1차다. 한 회사 안의 클라이언트 분리는 project/goal 레이어로 가능하나, 예산·거버넌스 격리는 회사 단위가 가장 명확. 다클라이언트 시나리오는 회사를 복수로 두는 게 안전 (추정 — 공식 문서 미확인).

    Q5. "에이전트 장애나 LLM 호출 실패 시 복구는 자동인가?" — heartbeat 루프가 다음 tick에서 retry 시도, execution lock의 stale 처리도 자동. 다만 외부 도구(MCP/CLI) 실패는 skill 레벨에서 처리해야 하고, 시스템 차원의 dead-letter queue는 미확인. 운영 시 별도 모니터링 권장.

    4.5 mock 처리 경계

    데모 마지막 단계인 Publisher → Postiz upload + 다채널 예약 은 mock 처리한다. Editor review 승인 후 Publisher 에이전트가 호출되면 "Postiz CLI 호출이 성공했다"는 가짜 응답을 반환하는 skill을 붙인다.

    mock 이유 (spec §4.3 결정):

    • 진짜 Postiz 연결은 임팩트는 크지만 1~2시간 추가 셋업 필요
    • 인증/계정 의존성이 발표 중 실패 위험을 추가
    • 메시지 전달(=거버넌스와 org chart 작동 시연)에는 mock으로 충분

    실제 연결 시 추가 셋업: Postiz API key + 환경 변수 / agent-media 키 (UGC까지 확장 시) / Instagram·TikTok·YouTube 채널 OAuth / F&B 한국 채널(카카오톡 채널·네이버 플레이스·배달앱)은 Postiz 범위 밖 — 별도 publisher 에이전트 필요 (research/03 §9).

    이 경계는 발표 중 명시적으로 한 슬라이드로 짚는다 — "왜 mock이냐" 질문이 반드시 나오므로 선제 답변.

    4.6 데모 fallback (라이브 실패 시)

    spec §7 위험 표의 "라이브 데모 실패" 대응책을 따른다. 발표자가 즉시 전환할 수 있는 순서를 미리 합의한다.

    1. 사전 녹화 영상 재생 — D-2 / D-1 dry-run 중 가장 stable했던 회차를 풀 녹화해두고, 라이브 인스턴스가 응답하지 않으면 즉시 영상으로 전환. 영상은 음소거로 두고 그 위에 발표자의 라이브 내레이션을 입힌다.
    2. 캡처 슬라이드 walk-through — 영상마저 작동 안 할 경우, slide 15~22(spec §5.1)에 배치된 데모 캡처 슬라이드 8장으로 동일 시나리오 설명. 6 시연 항목 각각에 1~2장씩 매칭.

    전환 결정은 발표자 단독. 라이브 복구 시도는 최대 1분으로 제한하고 초과 시 무조건 fallback 1로 전환 — 청중 집중력 손실이 컨텐츠 손실보다 비용이 크다는 판단.

    5. F&B 마케팅 자동화 관점 시사점 — Q&A 토론 시드

    본 장은 결론이 아니라 토론 시작점 이다. 본 세션의 Q&A 40분에서 발전시킨다.

    앞선 4장까지가 Paperclip의 패러다임적 위치(2장) · 운영 메커니즘(3장) · Nevo David 패턴의 reference architecture(4장)였다면, 본 장은 그것을 커넥트브릭(젝터스튜디오)이 만들고 있는 F&B 마케팅 자동화 에이전트 컨텍스트로 끌고 와 그대로 / 바꿔서 / 버리고 의 세 갈래를 정리한다. 모든 항목은 작성자(송태영)의 가설이며, 청중의 실제 워크플로 모양 — 점주·셰프와의 거리, 다점포 여부, 한국 채널 비중, 위생법규 검수 부담 — 에 의해 검증·반박되어야 한다.

    5.1 Nevo 패턴 vs F&B 적용 매핑

    Nevo David의 콘텐츠 파이프라인(7-step) · UGC 비디오(agent-media) · 다채널 publisher(Postiz) · slop 룰북 · 휴먼 게이트 위치를, F&B 도메인에서 어떤 게 그대로 적용되고 어떤 게 재설계 필요한지 8개 영역으로 압축하면 다음과 같다 (출처: research/03 §9).

    영역 Nevo의 패턴 F&B 그대로 F&B에서 바꿀 것

    핵심 두 변경점 — (1) 음식 비주얼은 generative-only로 안 되므로 실촬 자산 파이프라인 을 병행해야 하고, (2) 한국 F&B publish 채널이 Postiz 박스 밖이라 별도 publisher 에이전트 가 필요하다. 이 두 가지만 인정하면 나머지(skill 도구화 / 휴먼 게이트 위치 / slop 룰북 / heartbeat 스케줄링)는 거의 그대로 이식 가능 하다는 게 본 장의 출발 가설이다.

    5.2 한국 채널 갭 — Postiz가 못 다루는 영역

    Postiz의 25+ 채널 리스트(X, Instagram, TikTok, YouTube, Facebook, LinkedIn, Reddit, Threads, Bluesky, Pinterest, Discord, Telegram, Medium, Dev.to, WordPress, Mastodon 등)는 글로벌 SaaS 채널 중심 이다. F&B 마케팅에서 한국 시장 매출에 직결되는 채널 중 다음은 박스 밖이다.

    • 카카오톡 채널 — 단골 리텐션·쿠폰·예약 알림. 비즈니스 메시지 API.
    • 네이버 플레이스 / 네이버 블로그 — 위치 기반 검색의 1차 진입점. F&B에서 가장 중요한 지역성 채널.
    • 배달앱 알림 — 쿠팡이츠 / 배달의민족 / 요기요 의 매장 공지·할인 이벤트 등록.
    • 인스타 DM 자동응답·예약 봇 — 인스타는 Postiz에 있으나 DM 응대 는 별도 영역.

    해결안은 두 갈래의 가설을 동시에 두는 게 안전하다.

    1. 별도 publisher 에이전트 + 한국 채널 어댑터 직접 개발 — Paperclip의 어댑터 추상(http, process, claude_local 등)으로 한국 채널마다 HTTP/CLI 래퍼를 만들어 publisher 직원 한 명에게 도구로 붙인다. Nevo의 Postiz 에이전트와 형태는 같지만 어떤 SaaS·API 위에 올라가느냐 만 다르다.
    2. 한국 SaaS 활용 — 스푼/플레이콘/채널톡 등 한국 마케팅 SaaS가 이미 일부 채널 통합을 제공한다. 빌드 비용 vs 라이선스 비용의 트레이드오프를 정량화해야 한다.

    F&B 특화 점은 위치 기반(네이버 플레이스가 핵심) + 배달앱이 사실상 또 다른 매출 채널 이라는 점이다. 이 두 채널의 비중이 자사 고객사 분포에서 어느 정도인가 — 가 5.6의 토론 시드 4번으로 이어진다.

    5.3 실촬 + generative 하이브리드 — 음식 비주얼

    agent-media의 talking head는 사진 없이 description으로 캐릭터를 생성 하고 char_xxxxxxxxxx ID로 시리즈물 일관성을 유지한다 (research/03 §4). F&B에서 이걸 셰프/사장님 이미지 로 활용하는 건 부분적으로 가능하다 — 공식 사장님 캐릭터 를 한 번 만들어 두면 인사·신메뉴 소개·이벤트 공지 등을 시리즈물로 시작할 수 있다.

    하지만 음식 B-roll 은 문제가 다르다. 음식 비주얼의 핵심 매력은 다음 세 가지인데, 셋 다 generative-only는 위험하다.

    • ASMR (라멘 면치기·치킨 튀김 소리·삼겹살 굽는 소리) — 오디오 자체가 콘텐츠인데 합성은 식별된다.
    • 현장 슬로모 — 김이 올라오는 순간, 치즈가 늘어나는 컷 — 실제 촬영의 우연성 이 핵심.
    • AI 합성 음식 사진 특유의 부자연스러운 광택 — F&B slop 룰북에 반드시 차단할 패턴 으로 포함되어야 함 (5.4 참조).

    권장 가설은 실촬 영상 라이브러리 + generative talking head 하이브리드 다. 셰프 talking head는 generative로 일관성·확장성을 얻고, 음식 B-roll은 실촬 라이브러리에서 길이·각도·조명 태그로 검색해 합성한다. 이때 콘텐츠 에이전트의 도구 셋에 실촬 라이브러리 검색 MCP 가 추가되어야 한다는 게 자사 빌드 부담 추정이다.

    5.4 위생/원산지/표기법 게이트 — execution policy 활용

    Paperclip의 executionPolicy는 이슈마다 review stage / approval stage 를 런타임 강제 로 붙일 수 있다 (research/02 §6, 본 리포트 3장). 이걸 F&B 콘텐츠 발행 게이트에 법규 검수 stage 로 강제 적용하는 것이 본 장의 핵심 활용 시나리오다.

    F&B slop 룰북 패턴 (research/03 §9 표 마지막 행):

    • 공허한 후기체 — "맛있어요 / 존맛탱 / 꼭 가보세요" 같은 증거 없는 형용사 만 나열된 문장.
    • AI 합성 음식 사진의 부자연스러운 광택·과채도·플라스틱 텍스처.
    • 계절 한정 문구를 사철 적용 — "벚꽃 시즌 한정" 이 7월에 그대로 살아 있는 경우 (Notion DB의 시즌 메타와 cross-check 필요).

    법적 필수 항목 (식품표시광고법 / 원산지 표시 / 알러지) 은 단순 가이드라인이 아니라 위반 시 행정처분 대상 이다. 따라서 verifier 룰북에서 다음 항목들은 severity 최상위 로 분류되어야 한다.

    • 원산지 — 한우/한돈/국내산/수입산 표기 누락 또는 과장.
    • 알러지 — 식품등의 표시기준 고시 13개 의무 표기 항목(메밀·밀·대두·우유·계란·땅콩·복숭아·토마토·게·새우·고등어·돼지고기·아황산류) 누락.
    • 표시광고법 — "100% / 최고 / 유일 / 의학적 효능" 등 입증 없는 절대 표현 / 과학적 근거 없는 효능 표현.

    이걸 verifier 에이전트의 자동 룰북으로 1차 차단하고, 통과한 것만 사람 reviewer 게이트로 올리는 2-stage가 운영 부담을 크게 낮춘다. 단, 자동 verifier도 환각 가능성이 있으므로 법규 검수만은 사람 sign-off 를 끝까지 유지 하는 것이 안전한 출발점이다 (research/02 §8 의 "리뷰어가 또 다른 에이전트면 환각이 단계적으로 전파될 수 있음" 잔여 위험과 일치).

    5.5 도입 의사결정 — 어느 단계에서?

    research/02 §9.2의 stage A/B/C를 커넥트브릭 컨텍스트로 다시 쓰면 다음과 같다.

    • Stage A — 사내 도구로(dogfood): 자사의 콘텐츠 발행 / 리서치 / 리포트 자동화 에 Paperclip을 먼저 도입. 위험이 적고, 자사 마케팅 에이전트의 미래 모습 을 사내 운영으로 미리 경험할 수 있다. 본 세미나 시리즈(세미나·컨설팅 리포트 발행 워크플로) 자체가 stage A 후보다.
    • Stage B — 제품 비교 학습: Paperclip의 거버넌스 모델(승인 큐 / execution policy / 8차원 budget hard-stop / activity log) 을 자사 제품 UX 벤치마크 로 사용. "엔터프라이즈 고객이 자사 마케팅 에이전트를 도입할 때 어떤 거버넌스 화면을 기대하는가" 의 사실상 표준이 될 가능성이 있다(가설).
    • Stage C — 통합 옵션: 자사 마케팅 에이전트를 Paperclip의 employee 로 HTTP/webhook adapter를 통해 등록. 엔터프라이즈 고객이 자체 Paperclip 인스턴스에 자사 에이전트를 고용 하는 시나리오. 시장 확장 옵션이지만, Paperclip 자체의 6개월 생존 가능성에 베팅하는 결정이라 시장 모멘텀을 더 본 뒤 결정해도 늦지 않다.

    D-day 권고는 Stage A부터 — 그것도 본 세미나 운영 워크플로를 후보로 — 라는 것이 작성자 가설이다. 5.6 토론 시드 2번에서 이를 청중의 1인 운영 가능성·ROI 관점으로 검증한다.
